## 1. 效力与边界

```text
安全 / 合规 / 不可逆风险 = 硬底线
现行铁律（R1/R3–R5/R8–R20）= 流程/交付门
```

- R21-R25 是**铁律的工程决策组**，用于方案选择与审查透镜；不新增独立门，不改变五阶段、轨道、完成定义、审查轮次、MCP 路由与工具链地板。
- 与 R1-R20 冲突时，R1-R20 的流程/交付门优先；R21-R25 只回答“方案怎么选”。
- 与用户显式指令冲突时用户优先（违反安全/合规/铁律的除外）。

- R21-R25 是铁律编号，与审查/优先级 P0–P3 无关。

## 2. 五类十八条

### 2.1 R21 核心思想

- **R21.1 第一性原理**：先理解需求背后的真实目标、约束与成功标准，再选方案；不直接套用既有模式。
  - 反例：因为“别人都用微服务”就拆服务，而真实目标是单机吞吐。
- **R21.2 本质优先（YAGNI）**：先解决本质问题；不为假设中的未来需求提前设计复杂系统。
  - 反例：只有一个实现时先造插件系统/配置中心。
- **R21.3 可维护的最简实现**：先守住长期可维护/可测试/可回滚下限，再选当前最简单、可靠、清晰的实现。
  - 判据：更少概念、更低变更成本、可被现有测试覆盖。

### 2.2 R22 简洁与设计

- **R22.1 KISS**：优先简单直接，避免不必要复杂度。
- **R22.2 DRY**：重复逻辑第三次出现，或有明确变更成本证据时才抽象；允许少量重复。
  - 阈值：两次重复通常可接受；第三次或“改一处要改多处”时再抽象。
- **R22.3 SOLID**：职责清晰、低耦合；接口/扩展点第二个真实变化点出现后再引入。
  - 不预造 `IFoo`/DI 层；只在有第二个实现或测试替身需求时引入。

### 2.3 R23 架构

- **R23.1 删除优先于兼容**：内部代码直接删；公共 API/数据结构走弃用窗口 + 迁移说明 + 回归测试。删除限于本次变更影响面，不主动清理无关死代码。
- **R23.2 不做未验证架构**：不引入未经验证的抽象、配置、间接层；先 spike/原型/证据。设计/spike 是验证手段，不禁止规划。
- **R23.3 最小可用、逐步演进**：MVP 只缩范围；每次修改建立在可运行系统上；不跳过验证与独立审查；缩范围需用户批准，或已写入经用户批准的验收标准；不得静默缩 scope。
- **R23.4 当前可用性优先**：不为未来可能复杂度牺牲当前产品可用性；用户可见行为优先。

### 2.4 R24 代码质量

- **R24.1 职责单一**：按变更原因拆分模块，避免一个模块承担过多职责。
- **R24.2 成熟方案优先**：优先成熟、稳定、维护良好的第三方库；复杂/安全敏感领域不手搓。
- **R24.3 依赖克制**：已有代码/依赖/文档优先；新增依赖需收益、成本、替代方案与退出策略。
- **R24.4 先检查再引入**：先查已有代码、依赖、文档和能力，避免重复建设。
- **R24.5 反对“优雅复杂度”**：优雅的判据是更少概念、更低变更成本，不是更多层/更多模式。

### 2.5 R25 工程决策

- **R25.1 长期可维护优先**：优先长期可维护方案，但以 R21.3 的“最简”为约束；不为假设未来过度设计。
- **R25.2 业务目标优先**：代码服务业务目标，不为展示技术复杂度。
- **R25.3 简单满足即不升级**：简单方案已满足需求时，不主动升级复杂方案；升级需可验证的新需求或瓶颈证据。

## 3. 裁决顺序

```text
0. 安全 / 合规 / 不可逆风险 + 现行铁律（R1/R3–R5/R8–R20）（硬底线）
1. 用户显式指令与验收标准          （目标；不违反硬底线）
2. 正确性与可验证性 R1/R20         （交付门槛）
3. 当前业务可用性 R23.4/R25.2
4. 在可维护下限内选择最简 R21.3/R22.1/R24.5/R25.3
5. 有测量证据时才优化性能
6. 优雅 / 抽象不构成独立目标
```

“最简”与“长期可维护”冲突时：默认先满足可维护下限，再取最简；只有在出现**复发变更、多个消费者、公共契约**等证据时，才允许为可维护性增加结构。

## 4. 冲突矩阵（C1–C10）

### C1 R22.1 KISS / R22.3 SOLID

- 冲突：简单直接 vs 职责抽象/扩展点。
- 裁决：设计时 R22.1 优先；R22.3 作为审查/重构透镜，只在第二个真实变化点出现后应用；不预先造接口/层。

### C2 R22.2 DRY / R24.5 过度抽象

- 冲突：消除重复 vs 不为少量重复抽象。
- 裁决：同一逻辑第三次出现，或“改一处要改多处”的成本有证据时才抽象；否则允许少量重复。

### C3 R24.2 成熟第三方库 / R24.3 依赖克制

- 冲突：优先成熟库 vs 不随意新增依赖。
- 裁决顺序：已有代码/能力 → 已有依赖 → 标准库/框架 → 成熟第三方（仅当总拥有成本低于自研）→ 最小自研。
- 边界：琐碎功能不加依赖；复杂/安全敏感领域不手搓；新增依赖必须写收益、成本、替代与退出策略。

### C4 R23.1 删除过时代码 / R14 版本克制

- 冲突：删除优先 vs 兼容层/迁移。
- 裁决：内部代码直接删；公共 API、数据结构、配置契约走弃用窗口 + 迁移说明 + 回归测试；不得静默破坏。
- 与 R14：R14 约束 major 版本升级，不保护内部死代码；R23.1 的删除限于本次变更影响面。

### C5 R23.3 MVP / R1、R20 完成门

- 冲突：最小可用 vs 验证/审查。
- 裁决：MVP 只缩小范围，每次修改建立在可运行系统上，不降低验证/审查标准；R1/R20、测试、独立审查仍必须满足；缩范围需用户批准或经用户批准的验收标准。

### C6 R21.3 当前最简 / R25.1 长期可维护

- 冲突：现在选最简 vs 为长期留结构。
- 裁决：默认满足可维护下限后取最简；有复发变更/多消费者/公共契约证据时，可维护优先；无证据不为未来设计。

### C7 R25.2 业务目标 / R21.1 本质问题

- 冲突：业务要快 vs 技术要解本质。
- 裁决：业务目标定义“为什么”，本质问题定义“做什么”；不以业务紧迫跳过正确性/安全，也不以技术本质为名做业务不需要的事。

### C8 R23.2 不做未验证架构 / 非简单设计

- 冲突：禁止未验证架构 vs 非简单任务必须设计。
- 裁决：设计/spike 是验证手段；禁止的是未经验证的抽象落地，不是规划本身。非简单任务仍走 brainstorming/writing-plans。

### C9 R23.4 当前可用性 / R25.1 长期结构

- 冲突：用户可见行为 vs 内部重构。
- 裁决：用户可见行为以当前可用性优先；内部结构可在无可见回归的前提下选择可维护方案；破坏性变更需迁移说明。

### C10 R21.1 第一性原理 / R24.2 成熟方案

- 冲突：从本质出发 vs 直接用成熟库。
- 裁决：第一性原理决定“是否必要/是否自建”；商品化需求默认成熟方案；只有成熟方案明显不匹配约束时才自研。

## 6. 十个决策场景

1. **为 10 行工具函数引入新库**：R24.3/R24.4 → 先查已有依赖/标准库；不为琐碎功能加依赖。
2. **两段相似代码**：R22.2 → 两次重复可接受；第三次或变更成本有证据再抽象。
3. **一个实现先造插件系统**：R21.2/R23.2 → 拒绝；等第二个真实实现。
4. **遗留模块的旧 fallback**：R23.1 → 内部直接删；公共契约先弃用 + 迁移。
5. **MVP 要求跳过测试/审查**：R23.3 + R1 → 缩范围可以，跳验证/审查不可以；缩范围需批准。
6. **无指标要求性能优化**：裁决顺序第 5 条 → 先测量；无证据不优化。
7. **“更优雅”的多层重构**：R24.5 → 除非更少概念/更低变更成本，否则拒绝。
8. **用户要求临时 hack**：用户指令优先；但需记录债务、迁移路径与回归验证。
9. **依赖 major 升级**：R14 → 非必要不升；R24.2 不要求追最新。
10. **删除公共 API**：R23.1 + R14 → 弃用窗口 + 迁移说明 + 回归测试，不立即删除。
