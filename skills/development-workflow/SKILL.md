# 开发方法

入口中的风险分级决定流程长度；本技能不再分类或增加第二套完成门。

## 从问题到方案

1. 复述要解决的问题、受众、当前行为与成功标准。先读相关实现和约定，区分事实、假设与偏好。
2. 只问会改变结果的问题，一次一问并给推荐选项；不要求用户回答能从环境查到的事实。
3. 明确目标仍有多种合理路径时，给出少量方案及代价，推荐最短且可维护的一条；高风险设计得到批准后再实施。
4. 说明有意改变的行为和保持不变的契约，避免把重构等同于重写需求。

## 影响清单与计划

- 找到入口、调用方、共享数据、配置消费者和相关测试；有合适分析工具则使用，没有则搜索并读源码。
- 列出修改点、需同步的文档/示例、风险与回滚方式，不凭文件数量推测影响。
- 用 WHEN/THEN 写可观察验收；按依赖把任务拆成可独立验证的小步，每步附现有命令或明确观察方式。
- 不把尚未创建的检查脚本当作已存在验证。计划过大就分批，每批保持可运行且有独立验收。
- 小计划留在回复；确需跨会话时落 `spec/<project>/`，复用项目已有规划目录，不增加第二套规格系统。

## 按批准范围执行

- 按依赖顺序一次处理清单内相关项，不顺手扩大范围；已覆盖的设计与授权不重复审批。
- 无冲突的修改或检查可并行，明确文件归属；依赖结果的步骤等结果再继续。
- 每个有意义的步骤运行对应检查。失败先定位原因，不能带着未解释失败宣称该步骤完成。
- 配置改变后走查实际消费者；重命名、移动和删除后搜索旧引用，区分历史记录与活跃配置。
- 已批准的多文件任务不会仅因“超过两文件”重新回到设计；新范围或实质新风险才更新计划。

## 交接

向实施者提供原始要求、批准设计、影响清单与验证方式；向审查者提供当前差异和观察输出。
交付前按验证技能核验需求及既有行为，说明剩余缺口。工程细节见 `references/engineering.md`。

需要结构分析且选择图谱能力时，按需读 `references/graph-refresh.md`；无图谱时可用源码搜索和显式影响清单继续，不能声称图谱已刷新。
